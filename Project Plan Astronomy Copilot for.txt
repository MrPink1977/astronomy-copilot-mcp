Project Plan: Astronomy Copilot for NINA
Core goal

Fork michelebergo/nina_mcp_server and turn it from a large collection of raw NINA API controls into an intelligent astronomy operator for Codex.

The first useful version should let you say:

“Check the whole observatory, explain anything that is wrong, and help me take a test image.”

Codex should then:

Read the NINA equipment state.
Check the camera, mount, guider and plate solver.
Identify obvious configuration or connection problems.
Take a test exposure when requested.
Analyze the result and recent errors.
Recommend one clear corrective action.
Execute equipment-changing actions only after approval.

The existing MCP already translates AI tool calls into NINA Advanced API requests and exposes extensive NINA control. We will reuse that instead of recreating the API bridge.

What we are building
Working name

Astronomy Copilot MCP

Later it could support APT, PHD2, Stellarium, Home Assistant and weather systems, but version one supports:

Codex
   │
   │ MCP
   ▼
Astronomy Copilot MCP
   │
   ├── High-level astronomy tools
   ├── Diagnostics and recovery logic
   ├── Session state and event history
   └── Existing NINA MCP functions
            │
            ▼
      NINA Advanced API
            │
            ▼
 Camera · Mount · PHD2 · Focuser · Solver
What we are not building

We are not rebuilding:

NINA
NINA’s sequencer
NINA’s device drivers
PHD2 guiding
plate solving
target scheduling
ASCOM
every raw NINA API endpoint

The fork already exposes much of NINA’s equipment and imaging surface. The upstream project reports broad Advanced API coverage and already includes event handling and some scheduler-related functions.

Our value is the layer that decides:

what information is relevant,
whether the equipment is ready,
why an operation failed,
what action should happen next,
and whether that action requires approval.
Version-one success criteria

Version one is successful when you can operate your current rig through Codex and complete this workflow:

1. Start NINA
2. Load the saved equipment profile
3. Start the Astronomy Copilot MCP
4. Ask Codex: “Check my observatory”
5. Receive a useful equipment report
6. Connect equipment
7. Take a test exposure
8. Diagnose a failure or evaluate the frame
9. Plate solve and center a target
10. Start an existing NINA sequence
11. Safely stop and park

It does not need autonomous overnight control yet.

Phase 1 — Run the existing MCP unchanged
Objective

Prove that the existing project can talk to your NINA installation before changing code.

This is essential. Otherwise, every later failure could be caused by your modifications or by the base installation.

Requirements

On the observatory laptop:

NINA 3.x
NINA Advanced API plugin
Python 3.10+
uv or a Python virtual environment
Codex MCP support
NINA running with the API enabled

The existing project expects NINA’s Advanced API, normally at:

http://localhost:1888/v2/api

The upstream documentation describes the MCP as a Python process that receives MCP calls and translates them into REST calls to NINA.

First verification

With NINA open and Advanced API enabled:

curl http://localhost:1888/v2/api/version

Expected result: JSON containing the API version.

Then run the existing MCP server exactly as documented.

Initial tests

Test only read operations first:

get NINA version
get camera status
get mount status
get guider status
get connected equipment
get loaded profile
get current sequence status

Then test one controlled write:

connect the camera
take one short exposure
stop the exposure
Deliverable

Create:

docs/BASELINE_TEST_REPORT.md

Record:

NINA version
Advanced API version
Python version
MCP launch command
which tools worked
which tools failed
exact error messages
your current equipment

Do not modify the MCP until this baseline works.

Phase 2 — Inventory and classify the existing tools
Objective

Understand what the fork already provides.

The repository advertises a very large tool surface. Presenting hundreds of tools directly to Codex can create poor tool selection and unnecessary risk.

Create a tool inventory

Generate:

docs/EXISTING_TOOL_INVENTORY.md

Classify every existing tool into these groups:

Group	Examples
Read-only status	camera state, mount state, temperatures
Low-risk control	start preview, change exposure
Motion	slew, park, unpark, focuser movement
Session control	start, stop or modify sequence
Environmental	dome, shutter, weather
File access	images, logs, sequence files
Administrative	settings, profiles, API configuration

Add these properties to each tool:

Tool name
Purpose
Read or write
Equipment affected
Reversible
Requires confirmation
Possible physical consequence
Useful to first release
Why this matters

Codex should not see 176 equally important operations.

A request such as:

“Get me ready to image Regulus”

should invoke one controlled workflow, not require the model to improvise across a large unstructured API.

Phase 5 — Add a session-state model
Objective

Prevent the agent from treating every command as an isolated request.

The copilot should know whether the observatory is:

OFFLINE
STARTING
CONNECTED
PREVIEWING
SLEWING
CENTERING
GUIDING
IMAGING
PAUSED
RECOVERING
PARKING
SAFE
ERROR
Why this matters

A command can be valid in one state and inappropriate in another.

Examples:

Do not change camera settings during an active exposure.
Do not park while a slew is underway.
Do not start guiding before the guide camera is connected.
Do not plate solve a saturated lunar frame.
Do not start a sequence while another sequence is running.

The existing project already has event-related work that can support a stateful, event-driven system instead of constant polling. Use that foundation rather than rebuilding it.

Phase 6 — Add approval and action policies
Objective

Let Codex help without allowing uncontrolled hardware movement.

Action levels
Level 0 — Automatic, read-only

No confirmation:

get status
read logs
inspect image metadata
analyze recent errors
calculate image scale
inspect sequence state
Level 1 — Low-risk writes

May execute with general approval:

change preview exposure
start or stop looping
connect software devices
take a test frame
start plate solving
Level 2 — Physical movement

Explicit approval:

slew mount
move focuser significantly
rotate dome
open shutter
unpark
initiate meridian flip
Level 3 — Session-ending actions

Explicit approval unless emergency policy permits:

stop sequence
park mount
close dome
disconnect equipment
shut down software or computer
Add a dry-run mode

Every workflow should support:

dry_run=true

Example response:

I would:
1. Stop the current preview loop.
2. Set exposure to 4 seconds and gain to 100.
3. Capture one frame.
4. Run ASTAP.
5. Slew by the returned offset.
6. Capture and solve again.

No commands were executed.

Example rule:

First inspect image dimensions, saturation, star count, exposure, gain,

Phase 10 — Your first complete workflow

The first end-to-end workflow should be:

prepare_for_imaging

Input:

{
  "target": "Regulus",
  "test_exposure_seconds": 3,
  "require_guiding": true
}

Process:

Check NINA and Advanced API availability.
Read the active equipment profile.
Connect required equipment.
Verify mount clock, location and tracking state.
Confirm the mount is unparked.
Verify camera settings.
Confirm PHD2 is reachable.
Slew near the target.
Capture a solve frame.
Check star count and saturation.
Adjust solve exposure if necessary.
Plate solve.
Recenter.
Start guiding.
Wait for acceptable guiding.
Capture a final test frame.
Return an imaging-readiness report.

This workflow alone would have handled much of the troubleshooting from your first NINA session.

The first practical starting task

Do not ask Codex to “build the whole astronomy copilot.”

Give it this first assignment:

Fork and baseline the upstream project without changing its behavior. Run its tests, inventory its files and MCP tools, document the architecture, identify the NINA Advanced API client layer, and produce a baseline report. Do not refactor or add features yet.

After that succeeds, the next assignment is:

Add a single new read-only MCP tool named get_observatory_status that combines existing NINA status calls into one normalized response. Add mocked tests and documentation. Do not modify existing raw tools.

That is the correct starting point: one useful vertical slice, fully tested, before expanding the system.
